# Общие таблицы в схеме `shared`

## Назначение

Схема `shared` хранит таблицы, которые используются несколькими функциональными схемами PostgreSQL. Перенос устраняет дублирование физической структуры, но не объединяет бизнес-записи с одинаковыми названиями.

Первая общая таблица — `shared.services`.

## Правила идентификации

Каждая перенесённая строка получает глобальный `shared.services.id`. Исходная идентичность сохраняется в тройке:

```text
source_schema + source_table + source_id
```

Тройка уникальна. Поля `name` и `shortname` не используются для автоматического объединения строк.

Таблица содержит максимальный набор колонок исходных таблиц: `name`, `shortname`, `status`, `category_id`, `options`, `cnt`, `tags`, `tenant_id`, даты и soft delete. JSON приводится к `jsonb`, числовые статусы — к `integer`; отсутствующие в источнике поля имеют `NULL`.

## Сохранение исходных таблиц

Исходные таблицы не удаляются. Перед созданием VIEW они переименовываются с префиксом `__`:

```text
clients.services       -> clients.__services
integration.services   -> integration.__services
fakes.service          -> fakes.__service
```

По тому же правилу переименовываются остальные источники. Резервные таблицы доступны для аудита и отката, но не используются приложением. Изменения в них вручную запрещены.

На исходном имени создаётся VIEW с фильтром по `source_schema` и `source_table`. Поэтому старые модели, SQL-запросы и формы продолжают использовать прежнее имя.

## Запись через VIEW

Для каждого VIEW устанавливается `INSTEAD OF`-триггер:

- INSERT создаёт запись в `shared.services` с фиксированным источником;
- UPDATE изменяет запись по глобальному `id`;
- DELETE выполняет soft delete;
- источник и служебные поля нельзя изменить через VIEW.

Изменения общей таблицы публикуются в `public.entity_changes`. Для `clients.services` и `integration.services` сохраняются текущие типы сущностей `ClientService` и `IntegrationService`.

## Ссылки

Перед cutover все найденные `service_id` переводятся с исходного ID на `shared.services.id`. Ссылки с FK получают внешние ключи на `shared.services`.

Ссылки без FK сопоставляются явно по схеме источника. Если соответствие отсутствует или неоднозначно, миграция должна быть остановлена до ручного согласования; угадывать сервис по одному числовому ID нельзя.

## Порядок новой миграции

1. Снять структуру, количество строк, контрольные суммы, FK, триггеры и ссылки.
2. Создать `shared.services` и уникальный mapping по `source_*`.
3. Перенести все строки без удаления источников.
4. Проверить покрытие всех `service_id`.
5. Снять старые FK и перевести ссылки на `shared.id`.
6. Переименовать физические таблицы в `__*`.
7. Создать VIEW и `INSTEAD OF`-триггеры.
8. Создать новые FK на `shared.services`.
9. Пересоздать актуальные записи синхронизации и проверить tenant visibility.

## Проверки после cutover

- количество строк в каждом VIEW равно количеству строк соответствующей резервной таблицы;
- каждая резервная строка имеет ровно одну запись в `shared.services`;
- нет потерянных и неоднозначных `service_id`;
- VIEW возвращают прежние имена и типы колонок;
- чтение, создание, изменение и soft delete через старые модели работают;
- ссылки `clients.accounts` и `support.credentials` проверяются внешними ключами;
- синхронизация и IndexedDB получают записи с глобальными ID;
- резервные `__*`-таблицы не участвуют в обычных запросах.

Автоматический `down` запрещён: обратный перенос требует проверки новых записей, обратного mapping и отдельного согласования, чтобы не потерять данные, созданные после cutover.
