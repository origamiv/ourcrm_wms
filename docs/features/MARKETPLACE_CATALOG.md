# Каталог маркетплейсов

Команда `integration:sync-catalogs` находит организации со включённой фичей `integration.marketplace_catalog_sync`, их активные аккаунты и связанные активные вебхуки и ставит задания в Redis. Для запуска одной площадки используется `--marketplace=wildberries`, `--marketplace=ozon` или `--marketplace=yandex_market`. За один запуск выбираются не более 10 вебхуков Wildberries и 100 вебхуков остальных площадок, начиная с самого старого `dat_last_run`. Опция `--tenant` ограничивает запуск организацией, `--limit` — количеством интеграций. Ручной последовательный режим сохранён как `--sync`.

Одна интеграция: `php artisan integration:sync-catalog WEBHOOK_ID`. Импорт создаётся до отправки задания, его ID сохраняется в очереди. Повторный запуск для активного аккаунта возвращает существующий импорт. Создание сериализовано блокировкой строки аккаунта в PostgreSQL.

Laravel Scheduler запускает массовую команду Ozon каждые 30 минут. Для других площадок команду можно запускать вручную или через настроенные задачи. В текущем окружении планировщик работает под Supervisor через `php artisan schedule:work` (`wms-scheduler`). Для окружений без Supervisor достаточно добавить в системный cron один вызов планировщика каждую минуту:

```cron
* * * * * cd /var/www/wms.our24.ru && php artisan schedule:run
```

Для включения фичи используется:

```bash
php artisan tenant:feature TENANT_ID integration.marketplace_catalog_sync 1
```

Состояние очереди показывается в **Обслуживание → Импорты**, активность вебхука сохраняется. Старый синхронный режим использует статус вебхука `3` и сессии в Redis; статус `3`, сохраняющийся более четырёх часов, автоматически восстанавливается.

Массовая команда пропускает аккаунты без обязательных реквизитов. Ответы 401/403 завершают импорт ошибкой, не отключая аккаунт автоматически. Временные сетевые ошибки, ответы 408/425/429/500/502/503/504 повторяются с задержкой, до пяти попыток задания. Синхронный режим сохраняет прежнее отключение аккаунта при отсутствующих реквизитах или 401/403.

В очереди одно задание загружает одну страницу: Ozon — 100 товаров, WB — 100 карточек, Яндекс Маркет — 200 предложений. После сохранения страницы импорт запоминает курсор и подтверждённое количество записей и отправляет следующее задание. При временном сбое повторяется текущая страница; ранее сохранённые страницы не загружаются заново. Ручное сопоставление товаров сохраняется. Неполная/пустая последняя страница WB или Ozon завершает проход даже при непустом курсоре; повторившийся курсор сообщает об ошибке вместо бесконечного цикла. Как в исходной реализации tswms, Ozon 404 с кодом `5` и сообщением `item not found` при запросе следующей страницы означает конец прохода; произвольный 404 остаётся ошибкой. Новый импорт всегда начинает полный проход заново.

Horizon в production запускает по пять обработчиков `imports_ozon`, `imports_wildberries`, `imports_yandex_market`. Для страниц Horizon сам ограничивает параллелизм; отдельная блокировка аккаунта не позволяет обрабатывать его дважды. Старые глобальные слоты используются только последовательным режимом. Ожидание блокировки не расходует сетевые попытки задания. Таймаут задания страницы — 1200 секунд, блокировки — 1260 секунд, обработчика — 1800 секунд; `retry_after` Redis не меньше 1860 секунд. После изменения кода/настроек нужен штатный перезапуск Horizon (`php artisan horizon:terminate`, Supervisor запустит его снова). Прогресс записывается на границах страниц.

### Сеть текущего сервера

Обработчики работают от `www-data`. Системное правило маркировки этого пользователя ранее направляло запросы в обход NetBird, вызывая таймауты API. С разрешения администратора добавлены только IPv4 HTTPS-исключения для `api-seller.ozon.ru`, `content-api.wildberries.ru`, `api.partner.market.yandex.ru`, перед маркировкой пользователя. Скрипт `scripts/marketplace_egress.py` обновляет DNS-адреса; системный таймер `wms-marketplace-egress.timer` запускает его каждые пять минут. Ошибка DNS сохраняет действующие исключения. TLS-проверка сертификатов включена. Эти настройки относятся только к текущему серверу.

Проверка: `systemctl status wms-marketplace-egress.timer` и HTTPS-запросы от `www-data`. Ответ без токена 401/403/404 подтверждает доступность сети, но не корректность реквизитов. Для отмены исключений остановить таймер и удалить только правила `mangle OUTPUT` с комментарием `wms-marketplace-https`.

Для каждой интеграции аккаунт выбирается по `webhooks.params.account_id`. Команда проверяет принадлежность аккаунта tenant и клиенту webhook. Для Яндекс Маркета аккаунт хранит Api-Key в `clients.accounts.token`, а идентификатор бизнеса — в `clients.accounts.src.credentials.business_id`. Каталог загружается методом `businesses/{businessId}/offer-mappings` с постраничным курсором.

Каждый запуск отображается в **Обслуживание → Импорты** с клиентом, marketplace, webhook ID, account ID, текущим статусом, обработанным количеством и текстом ошибки.

Результаты сохраняются в `wms.goods_marketplace`. Для Яндекс Маркета `external_id` и `offer_id` равны `offerId`, а `external_sku` содержит `marketSku`. Сопоставление выполняется по артикулу/offer ID и штрихкоду. Существующее ручное сопоставление не изменяется.

В разделе **Фулфилмент → Каталоги МП** связь с мастер-каталогом можно изменить карандашом в колонке «Мастер-каталог WMS». В поиске отображаются товары и категории; категории выбрать нельзя. После выбора товара нажмите «Сохранить». Ручное сопоставление получает статус `manual`.

Автоматическое создание мастер-товаров выключено по умолчанию. Для включения для организации используется:

```bash
php artisan tenant:feature TENANT_ID integration.auto_create_marketplace_goods 1
```

Для отключения используется значение `0`. При включённой фиче создаются минимальные карточка и товар WMS без категории.
