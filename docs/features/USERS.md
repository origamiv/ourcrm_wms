# Пользователи и авторизация WMS

## Интерфейс

- `/login` — Livewire: вход по email и паролю. Регистрация и восстановление по почте не реализованы.
- `/` — рабочее пространство Inertia + Vue 3; `/users` — управление пользователями организации для администратора.
- Визуальный источник: [Figma, экран «Администрирование — Пользователи»](https://www.figma.com/design/x2UByywVb3CQd8dbC9MKEi/?node-id=9-33020). Использованы Manrope, фон `#A8CAD4`, белые панели, зелёный акцент `#1E892F`, компактная таблица и фильтры колонок. Иконки экспортированы в `public/design/crm`; дополнительные разделы CRM и нереализованные действия не показаны.
- Фронт обращается к web-маршрутам с сессией и CSRF. Публичное API использует те же сервисы, без HTTP-вызовов между frontend-контроллером и API.

## Общие учётные записи

Источник и место записи — `public.users`. Роль администратора определяется по активному неудалённому назначению `main.role_user` с текущим `tenant_id` и активной неудалённой роли `main.roles` со `slug=admin`. Новые роли не создаются.

Статусы: `0` — новый, `1` — активен, `2` — блокирован, `3` — выполняется действие. Вход разрешён только при `1`, непустом `tenant_id` и отсутствии `deleted_at`. Сам вход статус не меняет. Email должен однозначно определять запись, иначе вход запрещён. В WMS новые и изменяемые email проверяются без учёта регистра среди всех общих записей, включая удалённые; исторические дубликаты автоматически не изменяются.

Администратор работает только со своей организацией. Поля: имя, фамилия, отчество, ник, email, телефон. Создание требует пароль с подтверждением (не менее 12 символов), назначает `tenant_id` администратора и статус `0`. Активация, блокировка, пароль, удаление и восстановление — отдельные действия. Восстановление возвращает статус `0`. Статус `3` доступен для отображения, но не назначается вручную. Роли и организация не редактируются.

Нельзя блокировать или удалять себя и последнего активного администратора. Общая запись меняется также для других приложений; их механизмы отзыва сеансов WMS не контролирует. WMS перепроверяет статус и роль при запросах, проверяет серверный отпечаток пароля/организации и отзывает собственные токены при смене пароля, блокировке и удалении.

## Хранение в браузере

IndexedDB `wms_cache` хранит разрешённые поля, версии записей и состояние загрузки. Ключ пространства: версия формата, ID пользователя, `tenant_id` и тип сущности. Пароли, хеши и токены в кэш не входят. При выходе очищается весь кэш WMS, остальные вкладки уведомляются через BroadcastChannel.

При открытии сначала показывается кэш, затем выполняется синхронизация. Первичная загрузка идёт порциями по 250 записей. Поиск, фильтры, сортировка и пагинация выполняются локально; пока начальная загрузка не завершена, интерфейс сообщает о неполном списке. Повторное открытие, фокус вкладки и восстановление сети запрашивают только изменения.

Записи и курсор сохраняются одной транзакцией IndexedDB. Удаления сохраняют локальную версию, чтобы поздний ответ не вернул удалённую запись. Подтверждённый ответ сохранения обновляет экран и IndexedDB, но не продвигает общий курсор. Конфликт версии возвращает `409` с текущими данными: пользователь может загрузить их или проверить свои поля перед повторным сохранением.

Web Locks сериализуют синхронизацию вкладок, BroadcastChannel уведомляет об изменениях. В браузерах без Web Locks версии записей защищают от старых ответов; возможна повторная передача уже применённых изменений. При недоступной IndexedDB работа продолжается в памяти с уведомлением.

Без сети доступно чтение ранее загруженных данных в уже открытом приложении, включая переход между главной и пользователями. Запись, офлайн-очередь, service worker и холодный запуск без сети не реализованы. Отзыв прав обнаруживается при следующем серверном запросе; сетевой сбой не считается отзывом прав.

## PostgreSQL и эксплуатация

Общий журнал синхронизации хранится в `public.entity_changes`, счётчики по организациям — в `public.sync_state`; [подключение сущностей и переход](SYNC.md). Токены Sanctum хранятся в существующей `public.personal_access_tokens`: имя `wms:<отпечаток>` связывает токен с текущим паролем и организацией без дополнительных колонок. WMS отзывает только свои токены. Пустая устаревшая таблица токенов в `wms` удаляется отдельной миграцией; откат её не восстанавливает. `public.personal_access_tokens`, `public.users`, `main.roles`, `main.role_user` должны существовать заранее; миграция не пересоздаёт их и не меняет учётные записи.

Триггер фиксирует INSERT, UPDATE, DELETE и TRUNCATE из любого приложения, включая SQL без изменения `updated_at`. При смене организации или ID создаётся удаление для старого ключа и запись нового. Мягкое удаление сохраняется как запись с `deleted_at`, чтобы поддерживать восстановление. В журнал попадает явный список разрешённых полей; секреты исключены.

Счётчик ревизий своей организации обновляется транзакционно с блокировкой до commit. Начальный снимок строится из последних событий каждого пользователя на фиксированную ревизию; изменения, совершённые во время загрузки, поступают следующей дельтой. Курсоры зашифрованы и привязаны к пользователю, организации, сущности, версии формата и поколению журнала; пересоздание журнала требует нового снимка. Журнал пока не очищается автоматически: без отдельного протокола сброса курсоров удалять старые события нельзя.

Триггер выполняется с правами владельца функции и фиксированным `search_path`, чтобы другим приложениям не требовалась запись в техническую схему WMS. Записи пользователей сериализуются на счётчике, поэтому длительные транзакции общей таблицы задерживают синхронизацию и другие записи. ClickHouse не участвует в оперативной доставке изменений.

Установка: настроить `DB_CONNECTION=pgsql`, `DB_SCHEMA=wms` и подключение к PostgreSQL; создать схему `wms` при её отсутствии (`CREATE SCHEMA IF NOT EXISTS wms`). Затем выполнить `composer install`, `npm ci`, `npm run build`, `php artisan migrate --force`. Регистрация старого ACL-пакета отключена, чтобы его миграции не создавали новые роли вместо использования общих. Установщик должен иметь права на создание объектов в `wms` и `public`, чтение пользователей и создание триггера на `public.users`. Первая миграция кратковременно блокирует запись пользователей для согласованной установки журнала. Откат общего журнала защищён от потери событий других сущностей; порядок описан в [SYNC.md](SYNC.md).
