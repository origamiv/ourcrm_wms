# Компании и контактные лица

В ленте администрирования доступны `/main/companies` и `/main/company_contacts`. Источники — существующие `main.companies` и `main.company_contacts`. Администратор видит и меняет записи только своей организации. Таблицы не пересоздаются.

Оба раздела поддерживают поиск, фильтр статуса и удалённых записей, сортировку по названию, страницы по 25 записей, создание, просмотр без редактирования, изменение и мягкое удаление с подтверждением. Контакты дополнительно фильтруются по компании; компания выбирается из неудалённых записей своей организации. Компанию с неудалёнными контактами удалить нельзя: сначала перенесите или удалите контакты.

## Поля и JSON

Обязательны `name`, `shortname`, `status` (0 — новый, 1 — активен, 2 — отключен, либо null). У контакта также обязателен `company_id`, опционально `val` — контактное значение. Поле `file` этой формой не меняется и в кэш не передаётся.

Компания: `fullname`, `inn`, `kpp`, `ogrn`, `phone`, `email`, `site`, `director_position`, `director_fio`, `bik`, `bank`, `rasch_schet`, `korr_schet`. Строки ограничены 255 символами, email валидируется. Прочие существующие столбцы не меняются.

По согласованному решению поля макета хранятся в существующем `src`:

| Ключ | Поле |
| --- | --- |
| telegram | Telegram |
| opf | Организационно-правовая форма |
| legal_address | Юридический адрес, текст из формы; `legal_address_id` не меняется |
| accountant_position | Должность бухгалтера |
| accountant_fio | ФИО бухгалтера |
| is_own | Наша |
| is_client | Клиент |
| is_partner | Партнёр |

Первые пять — строки до 255 символов или null; признаки — boolean. При сохранении переданные ключи объединяются с текущим JSON, остальные ключи сохраняются. Неизвестные ключи в запросе запрещены. В журнал синхронизации и IndexedDB попадают только указанные ключи `src`, а не весь JSON. Автоматический перенос значений из иных исторических ключей не выполняется. ОПФ и должности вводятся текстом; отдельные справочники для них не подключены.

## Транспорт и синхронизация

`POST /web/{directory}`, `PUT /web/{directory}/{id}`, `DELETE /web/{directory}/{id}`, где directory — `companies` или `company_contacts`. API имеет те же маршруты с `/api` вместо `/web`, требует Bearer Token. Web использует сессию и CSRF. Оба транспорта вызывают `CompanyDirectoryService`.

Создание возвращает 201, изменение и удаление — 200 с `{data: запись с version}`. Изменение и удаление требуют строковую `version`; устаревшая версия даёт 409 с `current`, неверные поля — 422, чужая запись — 404. `tenant_id` назначается сервером и запрещён в запросе. Произвольные JSON-поля не принимаются.

Данные читаются через `/web/sync/companies` и `/web/sync/company_contacts` (API — `/api/sync/...`). Каждая сущность имеет свой кэш и курсор. После подтверждения сервера обновляются IndexedDB и другие вкладки. Доступен просмотр сохранённых данных в открытом приложении без сети, изменения без сети отключены. Компании для контактов загружаются тем же механизмом синхронизации.

Миграция `000007` создала начальные события обеих таблиц в `public.entity_changes`. Текущая безопасная проекция JSON задаётся через `json_fields` в `config/sync.php`, а изменения публикует общий Laravel Observer. Состояние остаётся в `public.sync_state`.

## Подсказки DaData

При создании и редактировании компании поля «Название компании», «ИНН», «ОГРН» ищут организации и ИП в DaData. Поля «Банк» и «БИК» ищут банки. После двух символов и паузы 350 мс показываются до пяти вариантов с ИНН/КПП/адресом либо БИК. Выбор доступен мышью и стрелками с Enter, Escape закрывает список. Устаревшие ответы после изменения запроса, закрытия поля или формы не применяются.

Выбор компании заполняет `name`, `shortname`, `fullname`, `inn`, `kpp`, `ogrn`, `director_fio`, `director_position`, `src.opf`, `src.legal_address`; телефон и email — если DaData их вернула. Выбор банка заполняет `bank`, `bik`, `korr_schet`. `rasch_schet` вводится вручную: эти методы не возвращают расчётный счёт компании. Telegram, сведения о бухгалтере, признаки компании и внутренний статус сохраняют введённые значения. Выбор заполняет форму, запись сохраняется только обычной кнопкой создания/сохранения; после этого работает стандартная синхронизация.

Web: `POST /web/companies/suggestions/{type}`; API: `POST /api/companies/suggestions/{type}`, type — `party` или `bank`. Тело `{query: строка от 2 до 255 символов}`. Требуется администратор, не более 60 запросов в минуту. Ответ `{suggestions: [{value, detail, fields}]}` содержит только отображаемые данные и поля формы. Запросы идут с сервера, ключи в браузер и IndexedDB не передаются. Ответы не кэшируются. Недоступный сервис даёт 502, отсутствующая настройка — 503; ввод и сохранение реквизитов вручную остаются доступны. Ошибки авторизации провайдера не превращаются в выход пользователя из WMS.

Конфигурация: `DADATA_API_KEY` в `.env`, читается через `config/dadata.php`. `DADATA_SECRET_KEY` также хранится в `.env`, но для API подсказок не используется. Значения ключей не включаются в репозиторий. При изменении ключа сбросьте кэш конфигурации Laravel. Браузерные тесты отключают настоящий ключ и используют управляемые ответы; серверные тесты подменяют внешние HTTP-запросы.

Официальные контракты: [организации](https://dadata.ru/api/suggest/party/), [банки](https://dadata.ru/api/suggest/bank/).

Особенность рабочего сервера: PHP-FPM и CLI используют разные исходящие маршруты. Для HTTPS к DaData установлено точечное исключение из маркировки `www-data`, с обновлением адресов по DNS. [Настройка и проверка](../../ops/README.md).

## Контакты выбранной компании

Иконка «Контактные лица» в действиях компании открывает `/company_contacts?company_id={id}`. Сервер проверяет принадлежность компании текущей организации и передаёт `companyScope`. В этом режиме список содержит только контакты выбранной компании, смена компании в фильтре и форме недоступна. Новое контактное лицо автоматически привязывается к этой компании. Просмотр, редактирование и удаление доступны только для её контактов. Переход по общей вкладке «Контактные лица» возвращает обычный список всех доступных компаний.

Изменения выполняются через `POST /web/companies/{companyId}/contacts`, `PUT /web/companies/{companyId}/contacts/{id}` и `DELETE /web/companies/{companyId}/contacts/{id}`. API — те же пути с `/api` вместо `/web`, с Bearer Token. Общие правила полей, версий и прав сохраняются. `company_id` можно не передавать: он назначается сервером из маршрута; несовпадающее значение даёт 422. Контакт другой компании или чужая компания дают 404. Ограничение повторно проверяется в транзакции сервиса.

Контакты и компании по-прежнему используют общий кэш своих сущностей; фильтр компании не создаёт отдельный кэш и не сбрасывает курсоры. После первой загрузки доступен переход и просмотр контактов компании без сети, изменения отключены. Область компании сохраняется в URL при перезагрузке.
