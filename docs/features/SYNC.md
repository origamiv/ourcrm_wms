# Синхронизация сущностей

Общий журнал PostgreSQL — `public.entity_changes`. Поля: `revision bigint NOT NULL`, `tenant_id varchar(255)`, `entity text` (полный класс модели), `entity_id text COLLATE "C"`, `operation`, `data jsonb`, `created_at`. Для пользователей `entity = App\Models\User`; псевдоним транспорта — `users`. Уникальность события задаётся парой `(tenant_id, revision)` с `NULLS NOT DISTINCT`, поэтому одинаковые ревизии разных организаций допустимы. Числовые ID и UUID передаются строками. Индексы ограничивают поиск организацией и моделью, затем ревизией либо ID и ревизией.

`public.sync_state` хранит отдельную строку для каждого `tenant_id`: технический `id`, `tenant_id`, `revision` и `generation`. Уникальный ключ `tenant_id` использует `NULLS NOT DISTINCT` (PostgreSQL 15+): события без организации имеют одну отдельную строку, хранятся как источник общих данных. Разрешённые записи проецируются в разделы организаций по [правилу видимости](TENANT_VISIBILITY.md). Пустая строка tenant ID также не подменяется служебным значением.

`EntityChangeRecorder` атомарно создаёт счётчик либо увеличивает ревизию только нужной организации и записывает событие в PHP. Все модели внутри организации используют один счётчик; блокировка удерживается до commit/rollback. Другие организации могут писать независимо. Перемещение записи между организациями создаёт remove в старой и upsert в новой. При наличии внешней транзакции бизнес-запись и журнал фиксируются вместе; без неё recorder выполняет журнал в отдельной транзакции и пишет предупреждение.

Первый запрос синхронизации организации создаёт состояние и добавляет разрешённые общие записи; без событий её ревизия равна 0. Сброс поколения одной организации не инвалидирует курсоры других. Серверные операции пользователей блокируют строку состояния своего тенанта; проверка глобальной уникальности email дополнительно сериализуется advisory-блокировкой одного адреса.


## Контракт

`GET /web/sync/{entity_type}` использует сессию, `GET /api/sync/{entity_type}` — Bearer. Зарегистрированы `users`, `roles`, `permissions` и `permission_roles`, доступные администратору своей организации. Неизвестный псевдоним возвращает `404`, отсутствие прав — `403`. Реестр не загружает классы или таблицы по пользовательскому вводу.

Параметры: `cursor` либо `continuation`. Ответ: `entity_type`, `mode` (`snapshot`/`delta`), `changes`, `cursor`, `continuation`. Каждое событие содержит строковые `id`, `version`, операцию `upsert`/`remove` и `data` либо `null`. Снимок строится на фиксированную ревизию с детерминированной строковой сортировкой ID. Все страницы нужно дочитать по `continuation`; итоговый `cursor` используется при следующем посещении. Разные сущности имеют отдельные курсоры даже при общем для организации счётчике.

Курсор зашифрован и привязан к пользователю, организации, классу модели, версии формата и поколению журнала. Чужой курсор — `403`; устаревший формат/поколение — `409` и новый снимок. Старые `/web/users/sync` и `GET /api/users` работают адаптерами с прежней структурой ответа.

## Подключение сущности

1. Добавить в `config/sync.php` уникальный псевдоним, полный класс `entity`, квалифицированную таблицу `table`, список разрешённых полей `fields` и серверную проверку `authorize` в формате `[класс, метод]`, принимающую пользователя и возвращающую bool. В текущей версии выдача ограничена всей организацией; сущности с более узкими правами требуют соответствующей доработки фильтрации снимка и дельты до подключения.
2. Модель автоматически подключается к общему `EntitySyncObserver` из реестра. Обычные `save`, SoftDelete, restore и forceDelete публикуются синхронно. Для массовых `update`, `upsert`, импорта и таблиц косвенного влияния нужно вызвать `EntityChangeRecorder` явно в той же транзакции.
3. Начальный снимок добавлять через `EntityChangeRecorder::publishMany()`. `fields`, необязательные `json_fields` и `projector` в `config/sync.php` являются единственным источником payload. `id` всегда приводится к строке. Чувствительные поля включаются только явным перечислением; для `client_accounts` текущий контракт намеренно включает `pass` и `token`.
4. В браузере использовать `createEntitySync<T>(scope, alias)` и `EntityCache<T>`. `scope` включает версию, пользователя и организацию; кэш добавляет псевдоним сущности. CRUD остаётся специализированным: после подтверждения сервера передать каноническую запись с версией в `apply`.

Observer учитывает INSERT/UPDATE/DELETE через Eloquent и смену ID/организации. Мягкое удаление передаётся как `upsert` с `deleted_at`, полное удаление — как `remove`. Прямой SQL и `truncate` не создают событие; такие операции запрещены для штатной записи и должны явно вызывать пакетные методы `EntityChangeRecorder` в той же транзакции. Переименование PHP-модели требует миграции `entity`, обновления реестра и сброса поколения курсоров.

## Кэш и эксплуатация

IndexedDB версии 3 хранит записи и курсоры атомарно, раздельно по пользователю, организации и типу. Версии защищают от поздних ответов и повторного появления удалённых записей. Web Locks и BroadcastChannel разделены по тому же ключу. При выходе очищаются все типы, при недоступности IndexedDB используется память. Офлайн доступно чтение в уже открытом приложении, записи выполняются только онлайн.

Миграция `000003` переносит `wms.user_changes` в `public.entity_changes`, сохраняя события и ревизии. Она ограничивает ожидание блокировок пятью секундами, выполнение — минутой, обновляет поколение журнала. При уже существующей целевой таблице транзакция прерывается без перезаписи. Нужны права на создание объектов в `public` и `wms` и изменение триггеров источника. В браузере старое содержимое IndexedDB сбрасывается при обновлении версии.

Откат раннего преобразования журнала возможен только при отсутствии событий других моделей. Миграция PHP-writer имеет отдельный снимок обратной установки прежних функций и триггеров. Данные пользователей не удаляются. Автоматическая очистка журнала пока отсутствует: нельзя удалять события без протокола восстановления снимка и сброса старых курсоров. Журнал синхронизации не заменяет ClickHouse для аналитики.

Миграция `000004` переносит состояние в `public.sync_state`: начальная ревизия каждой организации равна максимальной сохранённой ревизии её событий. Сами события и их версии не переписываются. Старый глобальный счётчик удаляется, поколения создаются заново, браузер получает `409` и новый снимок. Нумерация продолжает расти отдельно по организациям. Откат восстанавливает глобальный счётчик только если ревизии событий разных организаций ещё не пересекаются; иначе он останавливается без удаления данных. Для обеих миграций заданы lock_timeout 5 секунд и statement_timeout 60 секунд.

Компании (`App\Models\Company`) и контактные лица (`App\Models\CompanyContact`) подключены миграцией `000007`. Третий необязательный аргумент `capture_entity_change` задаёт разрешённые ключи JSON-колонок; у компании это безопасная проекция `src`. Подробности — [COMPANIES.md](COMPANIES.md).

Для справочников без tenant_id в реестре установлен `global: true`: источник использует NULL-раздел журнала, а ответы HTTP, курсоры и версии — раздел организации пользователя. Файлы и иконки с tenant_id IS NULL подчиняются main.tenant_entity, как остальные сущности. [Контракт справочников](REFERENCES.md).

Миграция 000018 добавляет shared_initialized в public.sync_state и проекции общих записей для организаций. Миграция `2026_09_23_000002` сохраняет журнал и курсоры, удаляет только sync-триггеры/функции записи и переключает их на Laravel. Бизнес-триггеры и `INSTEAD OF`-триггеры совместимости VIEW остаются. После миграции нужно перезапустить долгоживущие queue-процессы, чтобы они загрузили observer и актуальное состояние совместимости. Подробности видимости — [TENANT_VISIBILITY.md](TENANT_VISIBILITY.md).
