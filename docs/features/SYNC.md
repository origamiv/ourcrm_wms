# Синхронизация сущностей

Общий журнал PostgreSQL — `public.entity_changes`. Поля: `revision bigint PRIMARY KEY`, `tenant_id varchar(255)`, `entity text` (полный класс модели), `entity_id text COLLATE "C"`, `operation`, `data jsonb`, `created_at`. Для пользователей `entity = App\Models\User`; псевдоним транспорта — `users`. Числовые ID и UUID передаются строками. Индексы ограничивают поиск организацией и моделью, затем ревизией либо ID и ревизией.

`wms.sync_state` остаётся общим транзакционным счётчиком и поколением журнала. Блокировка строки счётчика удерживается до commit/rollback: простая PostgreSQL sequence не обеспечила бы порядок фиксации. Все подключённые сущности используют этот счётчик; транзакции записи нужно держать короткими.

## Контракт

`GET /web/sync/{entity_type}` использует сессию, `GET /api/sync/{entity_type}` — Bearer. Сейчас зарегистрирован только `users`, доступный администратору своей организации. Неизвестный псевдоним возвращает `404`, отсутствие прав — `403`. Реестр не загружает классы или таблицы по пользовательскому вводу.

Параметры: `cursor` либо `continuation`. Ответ: `entity_type`, `mode` (`snapshot`/`delta`), `changes`, `cursor`, `continuation`. Каждое событие содержит строковые `id`, `version`, операцию `upsert`/`remove` и `data` либо `null`. Снимок строится на фиксированную ревизию с детерминированной строковой сортировкой ID. Все страницы нужно дочитать по `continuation`; итоговый `cursor` используется при следующем посещении. Разные сущности имеют отдельные курсоры даже при общем счётчике.

Курсор зашифрован и привязан к пользователю, организации, классу модели, версии формата и поколению журнала. Чужой курсор — `403`; устаревший формат/поколение — `409` и новый снимок. Старые `/web/users/sync` и `GET /api/users` работают адаптерами с прежней структурой ответа.

## Подключение сущности

1. Добавить в `config/sync.php` уникальный псевдоним, полный класс `entity`, квалифицированную таблицу `table`, список разрешённых полей `fields` и серверную проверку `authorize` в формате `[класс, метод]`, принимающую пользователя и возвращающую bool. В текущей версии выдача ограничена всей организацией; сущности с более узкими правами требуют соответствующей доработки фильтрации снимка и дельты до подключения.
2. Миграцией установить триггеры `wms.capture_entity_change` и `wms.capture_entity_truncate`. Первый аргумент — тот же полный класс модели, второй для записи — JSON-массив разрешённых полей. Список фиксируется в SQL миграции, изменение PHP-конфига само по себе триггер не меняет. `id` автоматически приводится к строке. Источник должен иметь `id` и `tenant_id`. Пароли, токены и другие секреты исключать.
3. В той же транзакции под блокировкой записи источника добавить начальные события существующих записей через `wms.append_entity_change`. Для начального снимка и последующих событий использовать один список разрешённых полей. Функция записи доступна владельцу инфраструктуры; обычные изменения фиксируются триггером SECURITY DEFINER с фиксированным search_path.
4. В браузере использовать `createEntitySync<T>(scope, alias)` и `EntityCache<T>`. `scope` включает версию, пользователя и организацию; кэш добавляет псевдоним сущности. CRUD остаётся специализированным: после подтверждения сервера передать каноническую запись с версией в `apply`.

Триггеры учитывают INSERT/UPDATE/DELETE/TRUNCATE, включая прямой SQL и смену ID/организации. Мягкое удаление передаётся как `upsert` с `deleted_at`. Полное удаление оставляет событие `remove`. Переименование PHP-модели требует миграции `entity`, обновления триггеров и сброса поколения курсоров.

## Кэш и эксплуатация

IndexedDB версии 2 хранит записи и курсоры атомарно, раздельно по пользователю, организации и типу. Версии защищают от поздних ответов и повторного появления удалённых записей. Web Locks и BroadcastChannel разделены по тому же ключу. При выходе очищаются все типы, при недоступности IndexedDB используется память. Офлайн доступно чтение в уже открытом приложении, записи выполняются только онлайн.

Миграция `000003` переносит `wms.user_changes` в `public.entity_changes`, сохраняя события и ревизии. Она ограничивает ожидание блокировок пятью секундами, выполнение — минутой, обновляет поколение журнала. При уже существующей целевой таблице транзакция прерывается без перезаписи. Нужны права на создание объектов в `public` и `wms` и изменение триггеров источника. В браузере старое содержимое IndexedDB сбрасывается при обновлении версии.

Откат преобразует журнал обратно только при отсутствии событий других моделей; подключённые триггеры новых сущностей также нужно откатить первыми. Данные пользователей не удаляются. Автоматическая очистка журнала пока отсутствует: нельзя удалять события без протокола восстановления снимка и сброса старых курсоров. Журнал синхронизации не заменяет ClickHouse для аналитики.
