# Товары

Левое меню **Товары**, первый пункт ленты **Товары**: `/goods/goods`.
Карточки: `/goods/goods/{id}/{view|edit|delete}`, создание — `/goods/goods/0/create`.
Доступ администраторам; записи изолированы по организации.

Используется существующая `goods.goods`. Поля: id, name, shortname, code,
parent_id, parent_code, type_good, type_unit, barcodes (JSON), articul (JSON),
is_from_external, is_category, status, level, goodcard_id, tenant_id и временные
метки с мягким удалением. В таблице первой отображается колонка `#`; есть код,
краткое название, статус и действия просмотра, редактирования и удаления.
Поиск учитывает название, код и артикулы. Признаки: 1 — Да, 2 — Нет;
статусы: 0 — Новый, 1 — Активен, 2 — Отключен. Уровень вводится явно,
по умолчанию 0. Связи родителя не могут образовывать цикл. Запись с дочерними
товарами нельзя удалить.

`articul` — необязательный массив строк, например `["000123", "SKU-001"]`.
До 500 артикулов, каждый до 255 символов; ведущие нули сохраняются.
`barcodes` редактируется отдельно, структура существующего JSON сохраняется.

## Карточки

Товар — первичная сущность; `goods.good_cards.good_id` ссылается на товар.
У одного товара может быть несколько карточек. `goods.goods.goodcard_id` —
необязательная ссылка на одну основную карточку этого товара. Создание товара
не создаёт карточку автоматически. Форма предлагает только неудалённые
карточки своей организации, принадлежащие редактируемому товару.
Создание и редактирование самих карточек отдельным интерфейсом пока не добавлено.

Миграция 000016 делает goodcard_id nullable, добавляет good_id (bigint FK)
и articul (JSON). Старые значения goodcard_id=0 переводятся в NULL. Обратная
связь восстанавливается для однозначных существующих основных карточек
той же организации; остальные старые карточки остаются без владельца.
Откат структуры блокируется, если он уничтожит связи или нарушит NOT NULL.

## API и синхронизация

- POST `/web/goods/goods`: создать.
- PUT `/web/goods/goods/{id}`: изменить.
- DELETE `/web/goods/goods/{id}`: мягко удалить.
- Bearer API: те же пути с `/api` вместо `/web`.
- Создание/редактирование требуют name, status, level; обновление и удаление —
  строковую version. Устаревшая версия возвращает 409 с актуальной записью.
- Ссылки проверяются на доступность и принадлежность организации. tenant_id
  берётся из авторизованного пользователя, передавать его запрещено.
- Чтение и дельты: `/web/sync/goods`, `/api/sync/goods`.
- Для выбора связей подключена синхронизация good_cards, type_goods, unit_goods
  (соответствующие таблицы схемы goods). Для good_cards доступно только чтение. Из карточек в кеш поступают только id, good_id, name,
  status, tenant_id и временные метки.

Миграция 000017 подключает общий журнал public.entity_changes и счётчики
public.sync_state. Обновления из SQL также фиксируются. Откат синхронизации
сохраняет исходные товары и карточки. Сохранение обновляет IndexedDB сразу;
просмотр ранее загруженного списка работает без связи.

## Справочники товаров

В ленте **Товары → Справочники** открывается обычное выпадающее меню:
**Типы товаров** (`/goods/type_goods`, таблица `goods.type_goods`) и
**Единицы измерения** (`/goods/unit_goods`, таблица `goods.unit_goods`).
Оба раздела поддерживают создание, просмотр, редактирование и мягкое удаление,
поиск по названию/краткому названию и фильтр статуса. Первая колонка — `#`.

Поля: name, shortname, status; tenant_id определяется пользователем.
POST/PUT/DELETE `/web/goods/{type_goods|unit_goods}` (PUT/DELETE с `/{id}`),
Bearer-аналог `/api/goods/...`. Проверяется version; конфликт — 409.
Используемый в товарах тип нельзя удалить, единицу также нельзя удалить,
если она используется в goods.good_cards.unit_id. Изменения справочников
синхронизируются в форму товара через существующие локальные кеши.
