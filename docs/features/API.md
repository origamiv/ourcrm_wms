# API WMS

Документация Scramble: `/docs/api`, JSON OpenAPI: `/docs/api.json`. Просмотр доступен администратору с web-сессией. Экспорт: `php artisan scramble:export --path=storage/app/openapi.json`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/auth/token` | Email и пароль → Bearer-токен на 12 часов; без предварительного токена |
| `POST /api/auth/logout` | Отзыв текущего токена |
| `GET /api/sync/{entity_type}` | Общая синхронизация; `users`, `roles`, `permissions`; параметры `cursor`, `continuation` |
| `GET /api/users` | Начальный снимок или дельта, параметры `cursor`, `continuation` |
| `GET /api/users/{id}` | Текущая запись своей организации |
| `POST /api/users` | Создание: `name`, `email`, `password`, `password_confirmation`; необязательно `last_name`, `middle_name`, `nick`, `phone` |
| `PUT /api/users/{id}` | Изменение профиля: `name`, `email`, `version` и необязательные поля профиля |
| `POST /api/users/{id}/{action}` | `activate`, `block`, `delete`, `restore`, `password`; обязательна `version`, для пароля — пароль и подтверждение |

Все операции, кроме получения токена, требуют `Authorization: Bearer …`; пользователи — роль `admin`. `tenant_id` берётся из авторизованной записи; передавать его в операциях записи запрещено. При создании и обновлении пользователя допустим status: 0 (Новый), 1 (Активен), 2 (Отключен). Поле необязательно: при создании по умолчанию 0, при обновлении без поля статус сохраняется. Действия activate/block сохранены для совместимости. Строковые ID и версии не теряют точность bigint в JavaScript.

Ответ одиночной операции: `{ "data": { …поля пользователя…, "version": "123" } }`. Создание возвращает `201`, остальные успешные операции — `200`. Поля пользователя перечислены в [описании реализации](USERS.md). Паролей и токенов в объектах пользователей нет.

Синхронизация возвращает `mode` (`snapshot` или `delta`), `changes`, `continuation`, `cursor`. Событие содержит `id`, `version`, `operation` (`upsert` или `remove`), `data` (объект пользователя либо `null`). Пока `continuation` не равен `null`, запросить следующую порцию с этим значением; окончательный `cursor` хранить для следующей синхронизации. Токены курсоров непрозрачны — разбирать или конструировать их на клиенте не нужно.

Ошибки: `401` — требуется вход, `403` — нет права или чужой курсор, `404` — запись недоступна, `409` — конфликт версии с `current` либо смена формата кэша, `422` — валидация/недопустимое действие, `429` — ограничение частоты. Изменение данных конфликтующей записи автоматически не повторяется.

Интегрированный frontend использует аналогичные операции `/web/users`, `/web/users/{id}`, `/web/users/{id}/{action}`, `/web/sync/users` с cookie-сессией и CSRF. Это отдельный транспорт общих сервисов, а не вызов публичного API из frontend-контроллера.

Общий контракт добавляет `entity_type` к ответу синхронизации. Старые маршруты пользователей сохраняют прежний ответ. Подключение типов и изоляция курсоров: [SYNC.md](SYNC.md).

[Роли и права доступа](ACCESS_CATALOGS.md) читаются через общие маршруты синхронизации. Создание: `POST /api/roles`, `POST /api/permissions`; обновление: `PUT /api/roles/{id}`, `PUT /api/permissions/{id}`. Поля и ограничения описаны по ссылке.

[Матрица ролей и прав](ROLES_RIGHTS.md): назначение и снятие права через `PUT /api/roles/{roleId}/permissions/{permissionId}`, чтение назначений через `/api/sync/permission_roles`.
