# Видимость записей по организациям

Для каждой таблицы с колонкой tenant_id действует единое правило:

- tenant_id заполнен: запись доступна только этой организации. Назначения main.tenant_entity её владельца не переопределяют.
- tenant_id IS NULL: искать main.tenant_entity по паре entity_type + entity_id. entity_type — полный класс модели (например App\Models\Company), entity_id — ID конкретной записи.
- Назначений нет: запись доступна всем организациям.
- Назначения есть: запись доступна только организациям, перечисленным в tenant_id назначений. Назначение с NULL tenant_id не разрешает доступ никакой организации.

Таблицы без tenant_id остаются общими: сейчас это main.modules, main.features и clients.doc_types. Для них main.tenant_entity не используется.

Видимость не заменяет права действий. Редактировать доступную запись с tenant_id IS NULL может только пользователь с активной ролью admin. Сохранение существующей записи не присваивает tenant_id текущей организации. Передача tenant_id в запросе изменения запрещена. Создание обычной записи по-прежнему устанавливает организацию автора; создание в справочнике без tenant_id оставляет его общим.

## Сервер

Общий scope visibleTo($tenant) из HasTenantVisibility доступен моделям BaseModel и User. Он применяется к спискам, прямым карточкам, выбору связанных сущностей, PDF и CRUD. Для raw SQL используется та же функция wms.entity_visible(kind, id, owner, viewer). Проверка административной роли учитывает видимость и самой роли, и назначения main.role_user (entity_type App\Models\RoleUser).

Служебные проверки целостности (например, запрет удаления используемого справочника), глобальная уникальность email и аутентификация не ограничиваются списком видимых записей.

Новые разделы должны применять visibleTo() при чтении и проверке ссылок. При сохранении нужно повторно проверить admin и видимость в транзакции, исключить tenant_id из изменяемых полей и использовать EntitySyncService::prepareWrite() перед блокировкой организации. Для таблицы без tenant_id при подключении синхронизации также обновляется список исключений wms.shared_entity_visible.

## Синхронизация

Отдельных таблиц журналов нет. public.entity_changes сохраняет исходное событие общей записи в разделе tenant_id IS NULL и адресованные организациям события в их существующих разделах. Недоступной организации отправляется remove без содержимого. Число событий общей записи зависит от числа организаций, уже имеющих public.sync_state.

Изменения main.tenant_entity через INSERT, UPDATE, DELETE и TRUNCATE порождают upsert/remove. UPDATE может менять организацию, ID и класс сущности. Непустой tenant_id самой записи имеет приоритет. Бизнес-таблица при изменении назначений не переписывается.

Поле public.sync_state.shared_initialized отмечает первую загрузку общих записей в раздел новой организации. Инициализация сериализована с общими изменениями. HTTP-курсоры и версии записей, включая общие справочники, относятся к организации пользователя. Версию для изменения нужно брать из её ответа синхронизации.

Сервер дополнительно проверяет текущую видимость перед выдачей содержимого журнала: старые курсоры и незавершённые снимки не раскрывают отозванную запись. Уже загруженная карточка закрывается, когда синхронизация получает её удаление; IndexedDB заменяет содержимое событием remove. Пока браузер офлайн, ранее загруженные данные остаются в нём до следующей успешной синхронизации.

## Миграция и проверки

Миграция 000018 сохраняет существующую main.tenant_entity, добавляет индекс, служебный признак состояния и функции/триггеры. Если таблица назначений отсутствует в новом окружении, она создаётся. Данные бизнес-сущностей и tenant_id не изменяются. Существующим организациям добавляются разрешённые общие записи; поколения курсоров сбрасываются. Версия кэша и IndexedDB повышена до 3, старое хранилище очищается при обновлении приложения.

Автоматический откат запрещён: возвращение прежних правил требует согласованного восстановления версии приложения и журнала, чтобы не раскрыть ограниченные записи.

Проверки: TenantVisibilityTest, обновлённые тесты справочников/синхронизации, сценарий отзыва доступа в браузере с проверкой IndexedDB и tests/Support/concurrency.php для параллельной записи/отзыва доступа.
