# Архитектура WMS

Ниже описана целевая архитектура. Состояние её внедрения отражено в [FOUNDATION.md](../features/FOUNDATION.md).

## Стек и структура кода

- Backend: Laravel 12, PHP согласно ограничениям `composer.json` (сейчас `^8.2`).
- `app/Models` — Eloquent-модели; `app/Http/Controllers` — HTTP-контроллеры; `app/Http/Requests` — FormRequest.
- `app/Services` — бизнес-логика и клиенты интеграций; `app/Jobs` — фоновые задачи; `app/Providers` — регистрация инфраструктуры.
- Предметные подкаталоги допустимы внутри этих слоёв. Отдельное дерево доменов в `Modules` не использовать.
- `routes` и существующий механизм route attributes — маршруты; `database/migrations` — миграции PostgreSQL; `database/seeders` — сидеры.
- `database/clickhouse` — DDL и миграционные SQL ClickHouse; `stubs` — шаблоны генерации; `tests` — проверки.
- Контроллеры выполняют валидацию, авторизацию, вызов сервиса и формирование ответа. В моделях описывать хранение и связи, не размещать управление бизнес-процессами.
- Выбор нового frontend-стека и транспорта очередей этим этапом не определяется. Проверять фактическую инфраструктуру, не переносить настройки исходного проекта автоматически.

## PostgreSQL и организации

- Использовать одну операционную БД PostgreSQL, разделяя функциональные модули схемами. Имена схем назначать при реализации соответствующих модулей.
- Таблицы в моделях, миграциях и межсхемных связях указывать с именем схемы: `schema.table`. Не полагаться на переключение `search_path` для выбора домена.
- Создание схем и таблиц оформлять миграциями. Откат не должен удалять чужие объекты схемы каскадно.
- Схемы соответствуют функциональным модулям, а не организациям и не каталогам `Modules` в PHP.
- Бизнес-сущности имеют `tenant_id` и SoftDeletes. Контекст организации получать из доверенного контекста авторизованного пользователя; механизм выбора организации определить при реализации авторизации WMS.
- Ограничивать организацией чтение, запись, lookup-связи и фоновые операции. Наличие `tenant_id` само по себе не обеспечивает изоляцию.
- Текущие остатки и операционные транзакции хранить в PostgreSQL.

## ClickHouse

- Использовать для исторических и статистических данных; не делать его источником текущих остатков и транзакционных решений.
- Передачу данных из PostgreSQL проектировать с обработкой повторов и сбоев. Конкретный механизм доставки определяется при реализации интеграции.
- История бизнес-сущностей и статистические запросы сохраняют границы организаций через `tenant_id`.
- DDL хранить в `database/clickhouse`, настройки подключения и секреты получать через конфигурацию и переменные окружения.

## API

- По умолчанию применять `auth:sanctum` и Bearer Token, а также проверку прав на конкретные данные.
- Использовать отдельные FormRequest для создания и обновления.
- Scramble формирует OpenAPI-документацию. Swagger подлежит удалению при технической подготовке основы.
- Описания контрактов и сценариев размещать в `docs/features` и `docs/help`. Изменения API и зависимостей выполнять в соответствующих задачах, а не считать их выполненными после принятия правил.
