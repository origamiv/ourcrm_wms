# Стиль кода и сущностей

## PHP и Laravel

- Следовать Laravel 12 и форматированию проекта; проверять изменённый PHP через `vendor/bin/pint --test`.
- Классы именовать в `StudlyCase`, методы и свойства — в `camelCase`, таблицы и поля — в `snake_case`. В маршрутах и идентификаторах не использовать дефисы.
- Таблицы именовать во множественном числе, модели — в единственном.
- Явно описывать `$table` с именем схемы, `$fillable`/`$guarded`, casts и связи.
- Контроллеры держать тонкими; бизнес-логику размещать в `app/Services`. Классы новой архитектуры не размещать в `Modules`.

## Создание сущностей

- Использовать адаптированные базовые классы и `stubs` по образцу исходного проекта. Их фактическая адаптация ещё предстоит: см. [статус основы](../features/FOUNDATION.md).
- «Создать сущность»: миграция, модель, контроллер, отдельные FormRequest для создания и обновления, Scramble/OpenAPI-документация и сервисы при необходимости.
- Бизнес-сущности используют `tenant_id` и SoftDeletes.
- «Создать справочник»: `id`, `name`, `shortname`, `status`, `tenant_id`, `created_at`, `updated_at`, `deleted_at`. Типы полей и значения статуса определять по задаче, не переносить предметные значения исходного проекта.
- Lookup-поля имеют суффикс `_id`; определять связи модели и объектное представление с суффиксом `_obj`. Доступность связанной записи проверять в рамках организации.

## Миграции и документация

- Изменения PostgreSQL оформлять миграциями с явно указанной схемой и обратимым `down`, когда безопасный откат возможен.
- ClickHouse DDL и миграционные SQL хранить отдельно в `database/clickhouse`.
- Писать документацию на русском, кратко и прикладно. Различать принятые соглашения и уже работающие возможности.
- Не менять frontend-стек и не добавлять зависимости без необходимости для задачи.
