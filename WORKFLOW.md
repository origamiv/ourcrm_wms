# Порядок работы над WMS

## Подготовка

1. Прочитать задачу, [AGENTS.md](AGENTS.md) и применимые документы [docs/rights](docs/rights/ARCHITECTURE.md).
2. Проверить `git status --short --branch`, зафиксировать для себя исходные пользовательские изменения и выполнить `git pull --ff-only`. При конфликте или расхождении веток не применять автоматический сброс, stash или force push.
3. Найти похожую реализацию через `rg`; проверить фактические зависимости, конфигурацию и [статус основы](docs/features/FOUNDATION.md). Целевые соглашения не означают, что инфраструктура уже реализована.

## Проектирование и реализация

1. Определить затронутые слои: `app`, `routes`, `database`, `stubs`, `tests`, `docs`; `resources` — только для задач интерфейса.
2. Использовать стандартные каталоги Laravel. Предметную группировку при необходимости делать внутри соответствующего слоя, без нового кода в `Modules`.
3. Для сущности определить схему PostgreSQL, принадлежность организации, связи, валидацию и авторизацию. Для API определить ответы, ошибки и документацию Scramble.
4. Держать HTTP-контроллеры тонкими, бизнес-логику размещать в сервисах, фоновые операции — в jobs.
5. Менять только необходимые файлы. Генераторы и базовые классы адаптировать к WMS, а не воспроизводить унаследованные интеграции.
6. Обновлять описания API в `docs/features` и пользовательские сценарии в `docs/help`. При реализации основы обновлять её статус.

## Проверка и завершение

1. Выполнить проверки по [TESTING.md](docs/rights/TESTING.md). Для документации достаточно проверки ссылок, согласованности и diff.
2. Проверить `git diff --check` и `git status --short`. Добавить в индекс только файлы задачи, затем проверить `git diff --cached --check` и содержимое staged diff.
3. Сделать коммит с русским сообщением и автором из `AGENTS.md`, затем push в текущую ветку, включая `master`. Не включать посторонние правки.
4. При неудаче коммита или push сообщить точную причину; не обходить ограничения force push.
5. В отчёте указать результат, проверки и хеш коммита со статусом push. Деплой и миграции на рабочей БД выполнять только в рамках соответствующей задачи.
