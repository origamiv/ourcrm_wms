# Правила работы в репозитории WMS

## Обязательные правила

- Общаться и документировать работу на русском языке.
- Перед любой работой проверить `git status --short --branch` и выполнить `git pull --ff-only`. Если обновление невозможно без вмешательства в пользовательские правки, не сбрасывать и не прятать их автоматически; сообщить причину.
- После каждой выполненной работы сделать коммит и push в текущую ветку, включая `master`. Не использовать force push.
- Автор каждого коммита: Вениамин Смородинский <origamiv@gmail.com>. Не указывать соавторство агента ни в метаданных, ни в сообщении коммита.
- Сообщение коммита писать на русском языке, кратко и по существу.
- Не менять несвязанные файлы, не откатывать пользовательские правки и не включать их в коммит задачи.
- Не коммитить `.env`, токены, ключи, дампы и пользовательские данные.
- Использовать стандартные каталоги Laravel внутри `app`. Новые доменные классы не размещать в `Modules`.
- Frontend — Inertia + Vue 3 + TypeScript, Livewire для отдельных серверных страниц. Стиль брать из Figma и `../front3`; локальные данные хранить в IndexedDB и обновлять дельтами после подтверждения сервера.
- Web-интерфейс использует сессию и CSRF, публичное API — Bearer Token. Оба транспорта вызывают общие сервисы.
- Синхронизация IndexedDB использует общий журнал `public.entity_changes`: `entity` — полный класс модели, `entity_id` — строковый ID. Состояние синхронизации хранить в `public.sync_state` отдельно по `tenant_id`; ревизии уникальны внутри организации. Новые таблицы журналов по сущностям не создавать; подключать типы по [SYNC.md](docs/features/SYNC.md).
- Токены Sanctum хранить в существующей `public.personal_access_tokens`, не создавать таблицу токенов в схемах модулей.
- Пользователи читаются и изменяются в `public.users`; статусы: 0 — новый, 1 — активен, 2 — блокирован, 3 — выполняется действие. Роли брать из `main.roles` и `main.role_user`.
- PostgreSQL — одна операционная БД с отдельными схемами функциональных модулей. ClickHouse — история и статистика.
- Бизнес-сущности используют `tenant_id` и SoftDeletes. Изоляцию организаций обеспечивать при чтении, изменении и связывании данных.
- API по умолчанию защищать Bearer Token через `auth:sanctum`, если задача не задаёт иной режим.
- Целевой инструмент документации API — Scramble/OpenAPI. Новую документацию Swagger не добавлять.
- Таблицы именовать во множественном числе, модели — в единственном. В маршрутах и идентификаторах не использовать дефисы; для разделения слов в маршрутах и полях использовать `_`.
- Валидацию выполнять через FormRequest с отдельными классами для создания и обновления.
- Контроллеры, модели, request-классы и миграции создавать на основе адаптированных базовых классов проекта и `stubs`. Если нужный шаблон ещё не адаптирован, привести его к правилам WMS в рамках задачи, не копировать старую предметную логику.
- «Создать сущность» означает создать миграцию, модель, контроллер, request-классы для создания и обновления, Scramble/OpenAPI-документацию и сервисы при необходимости.
- «Создать справочник» означает поля `id`, `name`, `shortname`, `status`, `tenant_id`, `created_at`, `updated_at`, `deleted_at`.
- Lookup-поля заканчиваются на `_id`; в модели определять связи, в объектном представлении использовать суффикс `_obj`.
- Описания публичных API хранить в `docs/features`, пользовательские сценарии — в `docs/help`.
